# 评审与改进

让每条发现对应到当前版本、可观察的问题和可重复的复验。做新的界面方案，或评审任务路径、信息层级和交互时，使用 `product-ui-design-review`。

## 确定范围与基线

- **确定交付。**「评审」「给建议」「先讨论」交付发现、改法和验收方法。「评审并改进」「按批注修改」包含实施与复验。用户指定条目时，按原编号对应到修改项和仅报告项。
- **已有评审与批注。** 先读原意见。按页面、角色、控件和触发状态在当前版本复查，分清仍存在、已经修复和证据不足。保留可以同条件复测的截图或记录。
- **未提交代码。** 核对仓库、分支和 worktree。用 `git status --short`、`git diff --cached`、`git diff` 和 `git ls-files --others --exclude-standard` 确认暂存版、工作区版和相关新文件。部分暂存的文件分别核对两版。已有修复的条目记录修复所在版本，交接时说明用户要交付的版本是否包含它。
- **只有片段或只读时。** 交付可核实的发现、可直接应用的改法和复验步骤。注明证据来自用户提供的记录，以及修改或验证进行到哪里。

## 评审

1. 按改动追到实际入口、共享调用方、数据来源和最终结果。选查相关边界，例如历史数据、权限或对象切换、迟到响应、返回、重试和部分成功。
2. 按任务影响排序，先处理错数据、错对象和任务中断。评审组件、composable 或 service 的拆分时，说明可复用的规则、状态归属或具体回归，结构建议单独标明。
3. 每条写清 `位置 → 触发条件 → 观察结果与影响 → 改法 → 验收条件`。位置用代码行号、截图或操作步骤定位。标明证据来源，缺少运行证据时给出补验方法。

## 改进与复验

1. 逐条修复范围内仍存在的问题，复用现有组件、业务规则和测试入口。按项目约定处理暂存区、生成物和 OpenSpec 记录，保留无关工作区改动。仅报告项给出证据与建议。
2. 在对应的修复版本上复验触发场景和相邻正常路径。界面复测沿用相同角色、数据和视口。按影响范围运行定向回归、类型检查、lint 或目标端构建。已有诊断对照改动前基线。
3. 按原条目交付改动位置、已验证的版本和环境、结果及待办。测试记录只有执行次数时，将通过情况标为待核实。涉及演示或部署时，核对页面或接口实际加载的版本，并分别报告源码修复与运行结果。

## 已有案例

- **TopPartner · 供应商详情与收款概览。** 未提交改动中，概览慢请求拖住整页。修复把加载和重试放在概览区，供应商资料和授权入口可以先用，并防止切换账号后的旧响应覆盖页面。历史账单缺少 `final_amount` 时保留账数、提示待核对数量，并隐藏受影响分组的总金额。全部金额已知且合计为零时显示 `¥0.00`。复验覆盖慢请求、重试、账号切换、缺值和零值。
- **智慧厨房 · 周排餐复制。** 核对页展示来源周，提交时只传计划 ID。来源计划在核对后改期时，原请求会从改期后的那一周复制。修复后，请求携带确认时的 `sourceStartDate`，服务端重新核对来源。核对后改期应拒绝整批，原草稿继续可用。同次修复还验证了旧数据中明细日期为空、可由 `dayIndex` 推导的正常情况。
